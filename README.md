# CampusPulse

A verified college event-discovery and event-management platform: students
discover events, enrol, get a QR entry pass, check in, and download
certificates; club organizers create/manage events and scan attendance;
administrators verify clubs and approve events.

> **Read this first.** This codebase was generated in a sandbox with no
> Flutter/Dart SDK and no network access to install one. Every file below is
> hand-written to be correct, but **has not been compiled or run**. Before
> anything else, follow "First run" below — expect to fix a handful of
> small issues (an import, a generated-file gap, a package version bump)
> that only a real `flutter analyze` / `flutter pub get` can surface.

## 1. Product overview

- **Students**: verified college-email accounts, browse/filter published
  events, follow clubs & categories, get notified, enrol with one tap,
  favourite events, hold a QR entry pass, download certificates after
  verified attendance.
- **Organizers**: create/edit draft events, submit for approval, manage
  registrations, scan QR codes for attendance, issue certificates once an
  event is completed.
- **Administrators**: verify clubs/organizers, approve or reject events
  (with a required reason on rejection), maintain the official calendar,
  cancel/unpublish events, see platform-wide stats.

Phase 1 explicitly excludes: payments, budgets, waitlists, volunteer
management, event feedback, AI recommendations, inter-college features,
chat, and general noticeboards. The architecture doesn't block adding them
later, but nothing here wires them up.

| Role | Screens |
|---|---|
| Student | Login, Register, Forgot Password, Verify Email, Home (feed + filters), Event Details, Favourites, My Events, QR Pass, My Certificates, Certificate Verify, Notifications, Profile |

## 3. Architecture

Feature-first, clean-ish layering:

```
lib/
  app/            # env, theme, router, root Riverpod providers, main.dart
  core/            # Result/AppFailure, domain enums/permissions, reusable widgets
  features/
    auth/          # domain (Profile, email validator), data (demo + supabase repos), presentation
    events/        # events feed + details, enrolment eligibility logic
    favourites/    # optimistic favourite toggle
    enrolments/    # My Events, QR pass
    clubs/         # (follows live in events_repository for now — see TASKS.md)
    notifications/ # in-app notification centre
    attendance/     # QR scan-result mapping + organizer scanner screen
    certificates/   # My Certificates, verify-by-code
    organizer/      # dashboard, event CRUD, registrations, scanning, cert issuing
    admin/          # dashboard, approvals, club verification, calendar
```

Every feature follows: **domain** (models + pure business logic, unit
tested) → **data** (a `DemoXRepository` and a `SupabaseXRepository`
implementing the same interface) → **presentation** (Riverpod
controllers/providers + screens). Screens never call Supabase directly —
only through a repository interface, so demo mode is a drop-in swap
(`lib/app/providers.dart` picks the implementation based on
`Env.isDemoMode`).

`Result<T>` / `AppFailure` (see `lib/core/`) replace throwing exceptions
across repositories, so the UI always has a typed, user-safe message.

## 4. Prerequisites

- Flutter (current stable — 3.24+) and Dart 3.4+
- A Supabase project (free tier is enough) — only needed if you turn off
  demo mode
- A Firebase project with Cloud Messaging enabled — only needed for real
  push notifications
- Node not required; Supabase Edge Functions run on Deno via the Supabase CLI

**Why `flutter create .` first:** platform folders (`android/`, `ios/`,
`web/`, `linux/`, etc.) are generated by the Flutter tool from templates
tied to your installed SDK version, and this build sandbox couldn't run
that command. Running it once, in an already-populated Dart project,
safely fills in only the missing platform scaffolding — it will not touch
`lib/`. If your Flutter version prompts about overwriting `pubspec.yaml`,
say no / keep the existing one.

## 6. Live backend setup (Supabase)

1. Create a Supabase project, grab the Project URL and anon key into
   `.env` (`SUPABASE_URL`, `SUPABASE_ANON_KEY`), set `APP_DEMO_MODE=false`.
2. Install the Supabase CLI, then link and push migrations:
   ```bash
   supabase login
   supabase link --project-ref <your-project-ref>
   supabase db push        # runs everything in supabase/migrations/ in order
   ```
3. **Allowed college-domain configuration** — add your institution's real
   domain(s) (a placeholder `college.edu.example` is NOT usable for real
   sign-ups):
   ```sql
   insert into allowed_email_domains (domain) values ('yourcollege.edu.in');
   ```
   Do this via the Supabase SQL editor or `supabase db execute`. You can
   add more than one domain (e.g. student + staff domains).
4. **Storage buckets** — migration `20260801000009_storage.sql` creates
   `event-posters`, `club-logos`, `certificates` with their policies. If
   your Supabase version doesn't support bucket creation via SQL, create
   the three buckets by hand in the Dashboard with the same
   public/false + size-limit + MIME-type settings, then re-run just the
   `create policy` statements from that file.
5. **Initial administrator** — there is intentionally no in-app "become
   admin" flow (spec section 26). Register a normal account through the
   app, verify its email, then promote it directly in SQL as a one-time
   bootstrap step:
   ```sql
   update profiles set role = 'admin' where college_email = 'you@yourcollege.edu.in';
   ```
   From then on, only existing admins can change roles (enforced by
   `protect_role_column()` — see `docs/SECURITY.md`).
6. **Clubs & organizers** — as the admin, verify clubs and add
   `club_members` rows with `is_verified = true` for each organizer (a
   Clubs admin screen exists for verifying pending clubs; adding the
   initial member row is currently a SQL step — see TASKS.md).
7. **Seed sample data (optional, dev only)**:
   ```bash
   supabase db execute --file supabase/seed/seed.sql
   ```
   Read the comments in that file — club/category/domain rows seed
   directly, but events reference real `auth.users` UUIDs, so create the
   demo organizer/admin accounts first and fill in their UUIDs as shown.

## 7. Firebase / FCM setup

1. Create a Firebase project, add Android/iOS/Web apps, enable Cloud
   Messaging.
2. Put the **client-safe** config values (API key, app ID, sender ID,
   project ID) into `.env` — never the service-account JSON.
3. Generate a service-account key (Project Settings → Service Accounts),
   and set it as a Supabase Edge Function secret — never in the client:
   ```bash
   supabase secrets set FIREBASE_SERVICE_ACCOUNT_JSON="$(cat service-account.json)"
   supabase secrets set FIREBASE_PROJECT_ID=your-project-id
   ```
4. Deploy `fcm-send` (see section 9 below). Device-token registration
   happens client-side; wiring `firebase_messaging`'s token stream to the
   `device_tokens` table is stubbed as a `NotificationService` interface
   (`lib/core/services/` — see TASKS.md; the plumbing is not
   device-tested here since this sandbox has no emulator).

## 8. Android / iOS / Web configuration notes

- **Android**: after `flutter create .`, add `google-services.json`
  (Firebase) under `android/app/`, and set `minSdkVersion` to at least 23
  (required by `mobile_scanner`/camera plugins) in
  `android/app/build.gradle`.
- **iOS-ready**: the codebase avoids any Android-only API directly in
  `lib/` — camera/notifications go through plugin packages that ship iOS
  implementations. After `flutter create .`, add `GoogleService-Info.plist`
  and camera/notification usage-description strings to `Info.plist`. Not
  built or signed here (no macOS/Xcode in this sandbox).
- **Web**: `cached_network_image`, `qr_flutter`, `url_launcher` all support
  web. `mobile_scanner` falls back to the manual-token-entry field on web
  (see `AttendanceScanScreen`). After `flutter create .`, add the Firebase
  web config to `web/index.html` per the FlutterFire docs.

## 10. Scheduled reminder setup

`event-reminders` is a plain HTTP function, not a cron job by itself.
Schedule it with Supabase's `pg_cron` + `pg_net` (Database → Cron Jobs in
the Dashboard, or SQL):

```sql
select cron.schedule(
  'campuspulse-event-reminders',
  '*/20 * * * *',  -- every 20 minutes
  $$
  select net.http_post(
    url := 'https://<your-project-ref>.functions.supabase.co/event-reminders',
    headers := jsonb_build_object('Authorization', 'Bearer <service-role-or-anon-key>')
  );
  $$
);
```

## 12. Known credential-dependent steps

- Anything under section 6/7/9/10 above requires a real Supabase/Firebase
  project — demo mode works with none of it.
- `mobile_scanner` camera scanning needs a physical device or emulator
  with camera support; use the manual token-entry field otherwise.
- Certificate PDF generation runs in the `issue-certificates` Edge
  Function (Deno + pdf-lib) — it only works once deployed against a live
  Supabase project with the `certificates` bucket created.

## 13. Troubleshooting

- **"flutter: command not found"** — install the Flutter SDK
  (flutter.dev) and add it to PATH; this repo doesn't bundle it.
- **`flutter create .` complains about an existing `lib/`** — that's
  expected and safe; it only fills in platform folders.
- **RLS "permission denied" errors while testing as admin** — confirm the
  account's `profiles.role` is actually `'admin'` (see section 6.5); RLS
  checks the live row, not a client-side flag.
- **Certificates never appear** — confirm the event is `completed`
  (not just `published`) and the student's `attendance_status` is
  `attended`; both are hard requirements enforced in the database, not
  just the UI (see `docs/CERTIFICATES.md`).
- **Push notifications don't arrive** — check `fcm-send` is deployed, the
  `FIREBASE_SERVICE_ACCOUNT_JSON`/`FIREBASE_PROJECT_ID` secrets are set,
  and the device actually has a row in `device_tokens`.
